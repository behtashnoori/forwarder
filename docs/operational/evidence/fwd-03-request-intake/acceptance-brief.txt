3. ACCEPTED ARCHITECTURE
────────────────────────────────

Commercial مالک transport_intent در ShipmentRequest است.

ساختار پذیرفته‌شده:
{"version":1,"steps":[{"mode":"road"},{"mode":"sea"},{"mode":"road"}]}

- ترتیب آرایه معتبر است.
- تکرار روش‌ها، حتی تکرار مجاور، حذف نمی‌شود.
- یک روش متمایز = single-mode.
- حداقل دو روش متمایز = combined.
- طبقه‌بندی، داده ذخیره‌شده را deduplicate نمی‌کند.
- انتخاب combined با کمتر از دو روش متمایز خطای فیلدی دارد.
- null یعنی توالی ثبت‌شده نداریم؛ نه مسیر عملیاتی خالی.

این داده خواسته اولیه مشتری است.
RouteLeg، مسیر اجرایی، وسیله، ترمینال، زمان‌بندی،
تعهد سرویس یا تأیید امکان حمل از آن ساخته نشود.

road / rail / air / sea مطابق ADR پشتیبانی می‌شوند؛
کاتالوگ موجود، مرجع انتخاب‌های معتبر باقی می‌ماند.

چرخه تجاری، Aggregate جدید، Workflow عمومی یا موتور
کریدور ایجاد نکن.

4. COMPLETE THE INPUT/READ/UPDATE CONTRACT
────────────────────────────────

قبل از کدنویسی اعتبارسنجی، جدول مختصر و قابل آزمون زیر
را در مستند مناسب همین مأموریت تکمیل کن:

INPUT CASE
→ NORMALIZATION
→ VALIDATION
→ PERSISTED VALUE
→ READ PROJECTION
→ ERROR/COMPATIBILITY RESULT

حداقل موارد:

الف) ورودی جدید:

transport_intent نام قرارداد پیشنهادی پذیرفته‌شده است.
transport_sequence در شاهد قبلی ورودی آزمایشی بوده است.
آن را بدون شاهد قرارداد قبلی، API پشتیبانی‌شده یا alias
رسمی فرض نکن.

هر alias واقعاً لازم، صریح و آزموده باشد؛
ورودی جدید را بی‌صدا حذف نکن.

ب) customer_choice و forwarder_suggestion:

در قرارداد جدید customer_choice، intent صریح و غیرخالی
الزامی است؛ forwarder_suggestion می‌تواند null بماند.

الزام فقط در frontend نباشد.
مسیر یا نسخه قرارداد جدید و سازگاری Client قدیمی روشن باشد؛
به یک flag دلخواه client برای دورزدن اعتبارسنجی اعتماد نکن.

ج) فیلدهای قدیمی:

ورودی scalar قدیمی معتبر طبق ADR پذیرفته شود.
از دو فیلد داخلی/بین‌المللی، ترتیب حدسی نساز.

وجود هم‌زمان intent و scalar به‌تنهایی تناقض نیست؛
معنای scope واقعی هر فیلد را بررسی کن.
ترکیب واقعاً ناسازگار را با خطای مشخص رد کن.

خواندن intent غیرnull اولویت دارد.
برای رکورد بدون intent، فیلدهای تاریخی با scope خودشان
نمایش داده شوند.

combined را به اولین/آخرین روش یا یک روش ساختگی تقلیل نده.

د) ویرایش، فقط اگر مسیر آن از قبل وجود دارد:

omitted، null و مقدار صریح جدید یکسان فرض نشوند.

Client قدیمی با نفرستادن transport_intent نباید توالی
ثبت‌شده را پاک کند. تغییر scalar نباید intent موجود را
بی‌صدا ناسازگار یا جایگزین کند.

قواعد و مجوزهای فعلی ویرایش حفظ شوند.
ویرایش در وضعیت ممنوع، صرفاً برای این قابلیت مجاز نشود.

تغییر ناسازگارِ Client قدیمی را با نتیجه سازگاری قابل فهم
مدیریت کن؛ موفقیت ظاهری با از دست رفتن داده ممنوع است.

کنترل هم‌زمانی موجود را رعایت و lost update مرتبط با
intent را بررسی کن. چارچوب عمومی ویرایش جدید نساز.

هـ) Client قدیمی:

محدودیت نمایش ترکیبی را در قرارداد پاسخ و UIهای تحت کنترل

نمایش می‌دهد.
