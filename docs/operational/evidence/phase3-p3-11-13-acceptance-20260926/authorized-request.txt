این توقف **درست و لازم** بوده. Codex دقیقاً همان‌جایی ایستاده که باید می‌ایستاد: Product تصمیم‌ها را داریم، اما سه تصمیم معماری باید قبل از ساخت رسماً پذیرفته شوند.

من هر سه ADR را بررسی کردم. **ADR-067 را قابل پذیرش می‌دانم، ADR-068 را با یک مرز کوچک قابل پذیرش می‌دانم، و ADR-069 را بدون یک اصلاح امنیتی مهم نباید همان‌طور که هست ACCEPT کنیم.**

### جمع‌بندی بررسی

**ADR-067 — ETA:** طراحی خوب و محافظه‌کارانه است. ETA را Projection مشتق‌شده نگه می‌دارد، SORهای Route/Event را دست نمی‌زند، ambiguity را با «غیرقابل محاسبه» جواب می‌دهد نه عدد ساختگی، Reference Versionها را pin می‌کند و history برآورد را پاک نمی‌کند. برای Cargoهای split هم تا وقتی پیشرفت کل بار قابل اثبات نباشد، ETA ساختگی نمی‌دهد. این دقیقاً همان چیزی است که می‌خواستیم.

تنها ترجیح معماری من این است که materialize شدن snapshot روی یک read معمولی، تبدیل به «نوشتن پنهان روی GET» نشود. اگر لازم است read باعث refresh شود، endpoint/Service contract باید صریحاً آن را به‌عنوان `ensure/refresh estimate` تعریف کند و idempotent باشد. این تغییر Product نیست و blocker هم نیست.

**ADR-068 — Closure:** طراحی‌اش خوب است: `completed` را به `closed` تغییرمعنا نمی‌دهد، policy نسخه‌دار می‌سازد، checklist از SORهای واقعی خوانده می‌شود، Admin exception کمبودها را پاک نمی‌کند و Close شدن Exception/WorkItem را خودکار نمی‌بندد.

فقط یک مرز را باید صریح کنیم:

> **Normal Close فقط از وضعیت `completed` مجاز است.**
> **Exceptional Admin Close هم در P3-12 فقط از `completed` مجاز باشد.**

یعنی:

```text
planned      → closed   ❌
in_progress  → closed   ❌
cancelled    → closed   ❌

completed
   ↓
normal close       ✅ اگر checklist پاس باشد

completed
   ↓
exceptional close  ✅ با Admin + دلیل + حفظ missing items
```

اگر روزی خواستیم مدیر از `in_progress` هم پرونده را ببندد، آن یک تصمیم محصولی جداست. این کار جلوی این را می‌گیرد که «exceptional closure» ناخواسته به یک bypass برای lifecycle تبدیل شود.

### نکته مهم ADR-069

اینجا یک مسئله امنیتی ظریف وجود دارد.

ADR پیشنهاد کرده یک `SECURITY DEFINER` function داشته باشیم که app آن را صدا بزند؛ app role عضو role ویژه نیست و raw update معمولی هم همچنان توسط trigger بسته می‌ماند. 

اما خود ADR هم می‌گوید DB برای اینکه بداند «actor واقعی چه کسی است»، به application service اعتماد می‌کند. 

پس DB می‌تواند ثابت کند:

```text
actor_id واقعاً Admin فعال همان tenant است ✅
target واقعاً Expert معتبر همان tenant است ✅
owner/version درست است ✅
history ساخته شده ✅
```

اما اگر application DB role مستقیماً function را صدا بزند و یک `actor_id` معتبر Admin بدهد، خود PostgreSQL راه مستقلی ندارد بفهمد واقعاً درخواست HTTP متعلق به همان Admin بوده یا نه.

بنابراین جمله‌ای مثل:

> «database independently authenticates the Admin»

نباید ادعا شود.

مرز درست این است:

```text
Application authentication
        ↓
binds real user identity

Application authorization
        ↓
authorizes TRANSFER_OWNER

PostgreSQL routine
        ↓
revalidates structural security:
tenant
role eligibility
current owner
version
history chain
atomicity
```

یعنی **Authentication/actor binding همچنان مسئولیت Application است** و Database مسئول جلوگیری از تغییر ساختاری owner بدون مسیر رسمی/history است.

این مدل هم قوی است و هم صادقانه.

Raw این همچنان باید fail شود:

```sql
UPDATE operational_shipment
SET primary_responsible_expert_id = ...
```

و history fabrication هم fail شود.

اما نباید در evidence ادعا کنیم که اگر کسی credential معتبر خود app database را کامل در اختیار گرفت، PostgreSQL می‌تواند تشخیص دهد که `actor_id` فرستاده‌شده واقعاً همان کاربر Login شده بوده است. اگر روزی بخواهیم در برابر compromised app DB credential هم این سطح را enforce کنیم، آن دیگر نیازمند یک identity-binding DB mechanism یا credential جداست و **Scope این Phase نیست**.

خود ADR نیز هدفش را حفظ write-once guard و ایجاد فقط یک مسیر استثنایی audited تعریف کرده است، که کاملاً درست است.  و همچنین درست تأکید کرده که WorkItem، Request assignment و DN10 entitlement نباید همراه انتقال owner خودکار تغییر کنند.
