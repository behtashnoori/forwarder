## Actual F01 mechanism assessment

Authorization grant stores immutable snapshots of owner-controlled monotonic root recipient-link, CRM recipient email/status and gamification email/verification generations alongside exact parent identity and normalized recipient hash. Every protected read/write/replay/dispatch compares these snapshots to fresh locked owner rows. Change-away and change-back increments twice, so equality restoration cannot revive an old snapshot. New explicit reissue snapshots current authority, revokes prior grant and preserves original horizon. No new JWT claim is needed because live persisted grant is authority.

The concrete PostgreSQL BEFORE UPDATE trigger contract advances OLD generation only for actual relevant transitions, rejects caller counter override/reset/decrement and overflow, and leaves unrelated/same-value updates unchanged. Counter initialization is metadata, not inference of historical identity; existing historical grants do not exist. RESTRICT deletion of referenced parents prevents delete/recreate identity reset. Trigger-generated values must be refreshed, not cached ORM snapshots.

This mechanism uses existing PostgreSQL facilities: row-level trigger functions expose OLD/NEW, can modify NEW before an update, and can abort operations with errors. Verified against [official PostgreSQL Trigger Functions documentation](https://www.postgresql.org/docs/current/plpgsql-trigger.html), §41.10.1. This confirms facility feasibility only, not actual migration/runtime behavior or the project's server version. No database was contacted. Ordinary SQL/ORM/bulk update paths must retain active triggers; privileged database administrators who can disable triggers are outside this bearer-product threat boundary and no Production hardening certification is claimed.

Customer-only trigger update changes only its held row/counter and does not reach policy/root/grant/action rows, preserving G01 order. Multi-root linkage paths lock all roots before customers. An old grant is denied by generation mismatch even when its pending action has not yet been relabeled BLOCKED; next dispatch claim checks fresh generation. Thus invalidation is enforceable without grant/action-lock inversion. SQLite application-only counters prove owner command semantics at most; direct SQL trigger guarantees and actual races require PostgreSQL Phase B evidence.
