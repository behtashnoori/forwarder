## Necessary F01 repair before Build

Live recipient equality is insufficient for the accepted requirement that recipient-link change ends authority. Root links can change away and back; CRM email/status or gamification email/verification can similarly revert. Row locks serialize individual operations but preserve no history of invalidating change, so an old unrevoked grant could resume read/write/replay/dispatch. The package does not specify monotonic generation binding or audited irreversible invalidation for these mutations.

Smallest in-scope repair: relevant owners maintain monotonic root recipient-link generation, CRM email/status authority generation, and gamification email/verification generation. Snapshot these in the Authorization grant at issuance and compare live on every read/write/replay/dispatch, using the documented lock order. Increment on each actual relevant mutation, including change-back; unrelated display/profile fields need not increment. Never reset/decrement generations or silently update a grant snapshot; reissue is explicit, revokes old grant, uses current certified recipient and preserves the original read horizon. Equivalent audited irreversible revocation on every relevant mutation is possible, but must avoid existing action-lock inversion. This is bounded exact-recipient grant lifecycle support under ADR §8/11/14, not a new identity system or product decision. A safe ABA mechanism feasibility probe can precede Build; actual owner mutation/DB/race proof remains Phase B.
